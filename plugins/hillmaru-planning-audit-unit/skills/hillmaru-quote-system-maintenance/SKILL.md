# 힐마루 견적관리시스템 유지보수

동훈그룹 골프장(힐마루 포천/창녕)의 구매 견적요청 → 업체 제출 → 선정 → 발주서 생성 흐름을 관리하는 웹앱(`server.js`)을 안전하게 고치고 확장하는 방법을 담은 스킬.

## 이 시스템의 구조

- 단일 파일 `server.js` (Node.js). Express가 아니라 손수 만든 `Router` 클래스가 등록 순서대로 라우트를 매칭한다.
- DB는 `@libsql/client`(Turso)를 `db.prepare(sql).get/all/run(...)` 형태로 감싸서 쓴다.
- xlsx 읽기/쓰기는 외부 라이브러리 없이 zip/xml을 직접 조작하는 자체 코드(`buildTemplateXlsx`, `readXlsxFirstSheet`, `setCellText`/`setCellNumber` 등)로 처리한다.
- 배포는 GitHub → Render. **GitHub push는 사용자가 명시적으로 요청하지 않으면 절대 먼저 하지 않는다** — 지금까지 이 프로젝트는 항상 사용자가 직접 GitHub에 올렸다.

## 작업 전에 반드시 확인할 것

1. 먼저 outputs 폴더의 `server.js`를 고친다. Downloads의 `server.js`는 "테스트를 다 통과한 최종본"만 올라가는 자리이므로 거기에 직접 손대지 않는다.
2. 손대려는 부분과 비슷한 기존 코드를 먼저 찾아서 컨벤션을 따른다 — 예: `BUYERS`/`BUYER_LABELS` 같은 고정 상수 목록 패턴, `getSites()`/`getItemPurchaseHistory()` 같은 조회 헬퍼, `vendorCategoryFilterUI`/`VENDOR_FILTER_SCRIPT`처럼 여러 페이지에서 재사용하는 UI 헬퍼.
3. xlsx 템플릿을 건드릴 때는 `setCellText`/`setCellNumber`가 **대상 셀 참조가 템플릿 XML에 이미 없으면 조용히 아무것도 하지 않고 넘어간다**는 점을 꼭 기억한다. 로컬 테스트용 더미 템플릿을 새로 만들 때, 실제로 쓰는 셀 좌표(예: 담당자명이 들어가는 칸)에 미리 아무 텍스트라도 채워두지 않으면 "고쳤는데 왜 반영이 안 되지?"가 아니라 애초에 테스트가 그 로직을 검증하지 못하게 된다.

## 안전한 수정 원칙 (왜 중요한지)

- **"고정"·"잠금" 요구사항은 UI만 숨기지 말고 서버에서 강제한다.** 예를 들어 "담당자를 고정해달라"는 요청을 드롭다운만 없애는 식으로 처리하면, URL 쿼리파라미터를 손으로 바꿔서 여전히 다른 값을 넘길 수 있다. 이 프로젝트에서는 발주서 다운로드 라우트가 `req.query.buyer`를 아예 참고하지 않고 `qr.manager_name`에서만 값을 가져오도록 백엔드에서 재계산하게 고쳤다 — "고정"이라는 말은 사용자 눈에 안 보이게 하는 게 아니라 값이 바뀔 수 없게 하는 것이기 때문이다.
- **기존 데이터와의 하위호환을 깨지 않는다.** 자유입력 필드를 고정 선택지(select)로 바꿀 때, 이미 저장된 값이 그 선택지 목록에 없을 수 있다 — 이런 값은 조용히 버리지 말고 "(기존값)"이라고 표시된 추가 옵션으로 살려둔다.
- **반복되는 UI/로직은 공유 헬퍼로 뽑는다.** 같은 패턴(예: 카테고리 필터, 일괄 선택 버튼)이 두 페이지 이상에 필요하면 각 페이지에 복붙하지 말고 공통 함수로 만들어 두 곳에서 같이 쓴다. 그래야 다음에 세 번째 페이지가 필요할 때도 덧붙이기만 하면 된다.
- **엑셀 내보내기 형식을 바꾸면 가져오기(import) 파서도 같이 확인한다.** 예: 품목명 앞에 번호를 붙여 내보내게 바꿨다면, 그 번호가 붙은 채로 재업로드됐을 때도 원래 품목과 정확히 매칭되도록 가져오기 쪽에서 번호를 벗겨내는 처리를 같이 넣는다. 내보내기만 고치고 가져오기를 그대로 두면 "다운로드 → 수정 → 재업로드"가 조용히 깨진다.

## 테스트 절차 (반드시 지킬 것)

이 환경의 셸(`mcp__workspace__bash`)은 **호출마다 완전히 새로운 격리된 환경**이 뜬다. 백그라운드로 서버를 띄운 호출과, 그 서버에 요청을 보내는 호출을 나누면 서버가 이미 사라진 상태라 연결이 거부된다. 그래서 "DB 초기화 → 서버 백그라운드 실행 → 테스트 스크립트 실행"을 **하나의 bash 호출 안에** 전부 넣는다:

```bash
rm -f /tmp/data/app.db && cd /tmp/testapp && \
nohup env PORT=5111 node server.js > server.log 2>&1 & \
sleep 2 && \
python test_round2.py && python test_round3.py && python test_round4.py && \
python test_round5.py && python test_round6.py
```

- 새 기능을 추가했으면 기존 `test_roundN.py`들은 그대로 두고(회귀 방지), 다음 번호로 새 테스트 파일을 추가한다.
- 기존 회귀 테스트를 전부 통과한 뒤에만 outputs의 `server.js`를 Downloads의 `server.js`로 복사한다. 복사 후 `diff -q`로 두 파일이 동일한지 확인한다.
- 여러 테스트 라운드가 같은 서버/DB를 누적해서 쓰기 때문에, "카테고리별로 정렬된 목록에서 첫 번째로 매칭되는 항목"을 그냥 집으면 이전 라운드가 만들어둔 데이터를 잘못 집을 수 있다. 정규식으로 방금 만든 이름을 앵커링해서(`re.search(r'방금만든이름.*?패턴', html, re.S)`) 특정하는 편이 안전하다.

## 자주 겪는 함정

- **PPT/문서 작업에서 이모지가 LibreOffice 미리보기에 tofu(깨진 박스)로 나온다** → 아이콘은 이모지 대신 짧은 텍스트 코드(예: `G2B`)를 색깔 배지 안에 넣는 식으로 대체한다.
- **`soffice --convert-to pdf` 실행 후 특정 파일명에 락파일이 남아 이후 rm/mv가 "Operation not permitted"로 계속 실패한다** → 그 파일명을 포기하고 완전히 새로운 ASCII 파일명으로 다시 저장하면 바로 해결된다. 락 자체를 풀려고 시간 쓰지 않는다.

## 출력 형식

이 스킬의 결과물은 문서가 아니라 **회귀 테스트를 통과한, 안전하게 수정된 `server.js`**다. 작업을 마치면 사용자에게 아래를 짧게 보고한다:

1. 무엇을 고쳤는지 (한두 줄)
2. 기존 회귀 테스트(+ 새로 추가한 테스트) 통과 여부
3. Downloads의 `server.js`에 동기화했는지 여부

GitHub push, 실제 배포(Render)는 사용자가 명시적으로 요청하지 않으면 하지 않는다.
